## 1. 设计目标

1. **单链接可访问**：构建产物是纯静态文件，不依赖 API、数据库、环境变量。
2. **闭环可操作**：学生报名 → 商家录用 → 签到 → 确认 → 结算 → 评价，全部在前端状态中真实流转。
3. **刷新不丢**：核心数据写入 `localStorage`，支持一键重置。
4. **部署可验证**：部署后必须通过 HTTP 资源检查 + 无头浏览器核心流程冒烟，才算完成。
5. **边界诚实**：支付、定位、认证均为演示态，界面明确标注。

**非目标：** 真实登录、真实支付、真实地图、服务端持久化、跨设备同步、消息推送、生产级风控。

### 2.1 为什么不做后端

| 方案 | 优点 | 缺点 | 结论 |
|---|---|---|---|
| 全栈 + SQLite | 真实多端持久化 | 需要服务器/进程/端口，单链接部署复杂 | 不采用 |
| Serverless API | 可持久化 | 需要账号、环境变量、冷启动、跨域 | 不采用 |
| **纯前端 + localStorage** | 零运维、单链接、演示稳定 | 仅单浏览器、非真实生产 | **采用** |

这是一个**产品原型**，不是生产系统。架构选择服务于「一个链接、可操作、可验收」。

## 3. 技术选型

| 层 | 选型 | 理由 |
|---|---|---|
| 框架 | React 19 + TypeScript | 组件化、生态成熟、类型安全 |
| 构建 | Vite 8 | 快速、产物简单、支持相对路径 |
| 路由 | `react-router-dom` 的 `HashRouter` | 静态托管刷新不 404，子路径部署无需重写 |
| 状态 | Context + `useReducer` | 规模小，避免引入 Redux/Zustand |
| 样式 | 原生 CSS + Design Tokens | 无 Tailwind 构建依赖，样式可控 |
| 图标 | `lucide-react` | 轻量、风格统一 |
| 持久化 | `localStorage` | 零依赖，满足演示 |
| 测试 | jsdom + tsx + 核心流程冒烟 | 不依赖真实浏览器，验证状态与交互 |
| 部署 | GitHub Pages（Actions 或手动上传 `dist`） | 由使用者自行部署，零服务器 |

**依赖控制：** 运行时依赖不超过 4 个（react、react-dom、react-router-dom、lucide-react），降低构建与部署风险。

## 5. 数据模型

### 5.1 基本约定

- 所有 ID 使用可读字符串（如 `job_cafe_01`），便于演示与调试。
- 时间使用 ISO 8601 字符串；展示时统一 `Asia/Shanghai`。
- 金额使用**整数分** `amountCents`，展示时除以 100；避免浮点误差。
- 状态使用字符串联合类型，禁止魔法字符串散落。
- 数据版本 `schemaVersion: 1`；升级时提供迁移或重置。


`localStorage` key：`weekendworth.demo.v1`。

**加载策略：**

1. 读取 → JSON parse → 校验 `schemaVersion` 与关键字段；
2. 失败/缺失 → 写入种子数据；
3. 写入失败（隐私模式/配额）→ 使用内存态，顶部提示「当前数据仅本次会话有效」；
4. 每次 dispatch 后持久化（节流 100ms 可接受，演示规模无需）。

### 5.4 数据关系

```text
Merchant 1 ──< Job 1 ──< Shift 1 ──< Application >── 1 Student
                                      │
                                      └── 0..1 Order >── 0..2 Review
                                             │
                                             ├── 0..1 Dispute
                                             └── 0..n WalletTxn
```

**约束：**

- 一个 `Shift` 的 `filledCount` 必须等于该班次下 `status in ['confirmed','checked_in','completed']` 的订单数。
- 同一学生同一班次最多 1 条 `Application`。
- 同一 `Order` 每方最多 1 条 `Review`。
- 录用/取消/签到必须幂等，重复调用返回原结果。

## 6. 状态机

### 6.1 报名

```text
applied ──商家录用──> accepted ──创建订单──> (order)
   │                    │
   ├──商家拒绝──> rejected
   ├──进入候补──> waitlisted ──有空位──> accepted
   │                    └──超时/放弃──> expired
   └──学生撤回──> withdrawn
```

### 6.2 履约单

```text
confirmed ──签到──> checked_in ──签退──> completed
    │                    │                 │
    ├─学生取消─> cancelled_by_student      ├─发起纠纷─> disputed ─> resolved
    ├─商家取消─> cancelled_by_merchant     └─结算─> settlement=released
    └─标记爽约─> no_show
```

### 6.3 班次

```text
open ──满员──> full ──有人取消──> open
  │              │
  ├──开始──> in_progress ──全部完成──> completed
  └──取消──> cancelled
```

### 6.4 结算

```text
escrowed ──商家确认工时──> pending_release ──24h无纠纷/演示加速──> released
    │                           │
    ├──商家取消──> refunded      └──纠纷──> held ──运营处理──> released / partial_refund / refunded
```

**演示加速：** 商家点击「确认工时」后立即释放，同时在时间线标注「真实规则为 24h 后释放」。

## 7. 匹配算法

### 7.1 硬约束（不满足直接不可报名）

1. 岗位 `active`、班次 `open` 且未满员；
2. 学生未报名过该班次；
3. 学生无同时间段已确认订单；
4. 班次时长 ≤ 8 小时；
5. 距离 ≤ 学生 `maxRadiusKm`；
6. 学生活跃报名数 < 3；
7. 学生无平台限制（信用 ≥ 40）。

### 7.2 评分（0–100）

| 维度 | 权重 | 计算 |
|---|---|---|
| 时间匹配 | 30% | 完全覆盖且前后有 1h 缓冲 = 1；完全覆盖但缓冲不足 = 0.8；边缘覆盖 = 0.5 |
| 距离 | 20% | ≤1km = 1；1km 到 maxRadius 线性递减至 0.4 |
| 技能 | 20% | 岗位必需技能全覆盖 = 1；有加分技能 = 0.75；无 = 0.45 |
| 信用 | 15% | `clamp((credit - 40) / 80, 0, 1)` |
| 偏好/历史 | 10% | 同类目完成过 = 1；收藏/浏览过同类 = 0.7；无 = 0.5 |
| 活跃度 | 5% | 近 7 天有登录/报名 = 1；否则 0.5 |

```text
score = 100 × Σ(weight_i × factor_i)
新学生（completedCount = 0）+5，上限 100
```

### 7.3 解释

每个推荐返回：

- 前 2 个正向理由，例如「时间完全匹配」「距离 1.2km，骑行约 6 分钟」；
- 1 个待确认项，例如「需要基础咖啡制作经验，可在报名备注说明」；
- 不展示受保护属性，不用学校层次/性别/民族参与评分。

### 7.4 示例

学生林小满，信用 108，可接受 2km，技能含「咖啡/沟通」，周六 09:00–18:00 空闲。

| 维度 | 因子 | 加权 |
|---|---|---|
| 时间 | 1.0 | 30 |
| 距离 1.2km | 0.88 | 17.6 |
| 技能匹配 | 1.0 | 20 |
| 信用 | 0.85 | 12.75 |
| 同类历史 | 1.0 | 10 |
| 活跃 | 1.0 | 5 |
| 新学生加成 | — | 0 |
| **合计** | | **95.35 → 95** |

### 7.5 公平性

- 不用性别、民族、学校层次、籍贯、外貌等属性；
- 新学生前 3 次报名获得 +5 曝光加权；
- 同一商家在同一列表最多占 2 个推荐位；
- 运营可下架违规岗位，但不能手工篡改学生信用。

## 8. 核心领域函数

```ts
canApply(state, studentId, shiftId): { ok: true } | { ok: false; code: ApplyError; message: string }
applyToShift(state, studentId, shiftId, note): AppState
acceptApplication(state, applicationId): AppState
rejectApplication(state, applicationId): AppState
waitlistApplication(state, applicationId): AppState
cancelOrder(state, orderId, actor, reason): AppState
checkIn(state, orderId, code): AppState
checkOut(state, orderId): AppState
confirmCompletion(state, orderId): AppState
submitReview(state, orderId, fromRole, rating, tags, comment): AppState
openDispute(state, orderId, role, reason, detail): AppState
resolveDispute(state, disputeId, resolution): AppState
resetDemo(): AppState
```

### 8.1 关键不变量

| 不变量 | 保障方式 |
|---|---|
| 不能超录 | `acceptApplication` 前重新计算班次已确认人数 |
| 不能重复报名 | 以 `(shiftId, studentId)` 唯一判定 |
| 不能时间冲突 | `canApply` + `acceptApplication` 双重校验 |
| 取消必须释放名额 | `cancelOrder` 重算 `filledCount`，触发候补 |
| 签到幂等 | 已签到直接返回当前状态，不重复写时间 |
| 结算只发生一次 | `settlementStatus === 'released'` 时拒绝重复结算 |
| 评价每方一次 | 按 `(orderId, fromRole)` 唯一判定 |
| 信用不越界 | 所有增减后 `clamp(0, 120)` |

### 8.2 错误码

| 码 | 场景 | 用户提示 |
|---|---|---|
| `SHIFT_FULL` | 班次已满 | 这个班次刚满员，可以加入候补 |
| `SCHEDULE_CONFLICT` | 时间冲突 | 与已确认班次冲突，先调整一个 |
| `DUPLICATE_APPLICATION` | 重复报名 | 你已经报名过这个班次 |
| `APPLICATION_LIMIT` | 超过 3 个活跃报名 | 最多同时报名 3 个班次 |
| `OUT_OF_RADIUS` | 超出距离 | 该岗位超出你的可接受距离 |
| `INVALID_STATE` | 状态不允许 | 当前状态无法执行该操作 |
| `INVALID_CODE` | 签到码错误 | 签到码不正确，请向商家确认 |
| `OUT_OF_WINDOW` | 不在签到时间 | 签到尚未开始/已结束 |
| `ALREADY_CHECKED_IN` | 重复签到 | 已签到，无需重复操作 |
| `SETTLED` | 重复结算 | 该订单已结算 |

## 9. 前端架构

### 9.1 路由

| 路径 | 页面 | 角色 |
|---|---|---|
| `#/` | 落地页 + 角色入口 | 公共 |
| `#/student` | 发现 | 学生 |
| `#/student/jobs/:jobId` | 岗位详情 | 学生 |
| `#/student/gigs` | 我的兼职 | 学生 |
| `#/student/work/:orderId` | 工作卡/签到 | 学生 |
| `#/merchant` | 商家工作台 | 商家 |
| `#/merchant/jobs/new` | 发布岗位 | 商家 |
| `#/merchant/jobs` | 岗位管理 | 商家 |
| `#/merchant/jobs/:jobId/applicants` | 候选人 | 商家 |
| `#/merchant/fulfillment` | 履约与结算 | 商家 |
| `#/admin` | 运营控制台 | 运营 |

**规则：**

- 路由守卫只做演示级校验：角色不匹配时显示「切换视角」提示，不强制跳转。
- 所有页面共享 `AppShell`：顶部品牌、角色切换、演示标识、重置。
- 移动端底部导航：学生「发现 / 我的兼职 / 消息」，商家「工作台 / 岗位 / 履约」；消息与个人资料为抽屉，不单独占路由。

### 9.2 状态流

```text
UI event → dispatch(action) → reducer → domain function → new state
         → persist(localStorage) → re-render
```

- 领域函数保持纯函数，输入 `AppState`，输出新状态；不直接读写 DOM/storage。
- 副作用（toast、滚动、下载）留在组件层。
- 选择器负责派生数据：岗位+商家+匹配分、班次剩余名额、学生可用余额。

### 9.3 组件原则

- 页面只做编排，业务规则进 `domain/`。
- 卡片/状态标签/匹配环等展示组件不依赖全局 store，通过 props 注入。
- 所有关键操作有 `data-testid`，用于线上冒烟。
- 表单使用受控组件 + 轻量校验，错误就近展示。

## 11. 部署与交付（使用者执行）

### 11.1 目标

- 托管：GitHub Pages（使用者自己的仓库）

- 链接：`https://<owner>.github.io/<repo>/`
- 构建：`base: './'` + `HashRouter`，支持仓库子路径与刷新

### 11.2 构建配置

```ts
// vite.config.ts
export default defineConfig({
  base: './',
  plugins: [react()],
  build: { outDir: 'dist', sourcemap: false },
});
```

- `public/.nojekyll` 防止 GitHub Pages 忽略下划线文件；
- `public/404.html` 将误输入的子路径重定向回 `./#/`；
- 资源文件名带 hash，避免缓存旧版本；
- 使用 Hash 路由，页面内地址形如 `/#/student`。

### 11.3 推荐：GitHub Actions

仓库内置 `.github/workflows/deploy.yml`：

1. 推送到 `main`；
2. 仓库 Settings → Pages → Source 选择 **GitHub Actions**；
3. 工作流执行 `npm ci`、`npm run build`，上传 `dist/` 并发布；
4. 完成后访问 `https://<owner>.github.io/<repo>/`。

### 11.4 备选：手动上传 `dist`

1. 本地执行 `npm run build`；
2. 把 `dist/` 全部文件上传到 `gh-pages` 分支根目录；
3. Settings → Pages → Source 选择 `gh-pages` / `root`；
4. 访问同上。

## 13. 已知限制

1. 数据只存在当前浏览器，换设备/清缓存即丢失。
2. 不是真实招聘平台，不提供真实岗位、合同、工资。
3. 支付、定位、认证均为模拟，不能用于真实交易。
4. Hash 路由的 URL 带 `#`，不利于 SEO；原型阶段可接受。
5. GitHub Pages 在部分网络环境可能访问慢；部署后需实测。
6. 无服务端风控，信用与认证可被本地篡改；仅用于演示。
7. 演示模式放宽签到时间窗口（定位仍为模拟），页面标注「演示模式已放宽」；规则函数保留真实窗口逻辑，便于单元测试。
