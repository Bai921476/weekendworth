## 1. 题目理解

题目是「大学生周末兼职撮合」，但真正要解决的不是「再做一个招聘信息墙」，而是三件事同时发生：

1. **信息要按周末班次组织**：学生关心「这周六 10:00–18:00 有没有活」，而不是一个模糊的「长期兼职」。
2. **双边都要降低风险**：学生怕被骗、怕白干、怕耽误课；商家怕放鸽子、怕招人慢、怕不会干。
3. **撮合必须走到履约**：只把电话给双方，和微信群没有本质区别。平台的价值在报名后的确认、到岗、结算与评价。

因此产品定位为：**大学城 3 公里内、以周末班次为单位的短工撮合与履约保障平台**。

## 2. 现状与痛点

> 说明：以下为基于题目背景和常见校园兼职场景的**问题假设**，不是已完成的用户调研数据。试点前需用 15 名学生 + 10 家商户访谈验证。

### 2.1 学生侧

| 痛点 | 具体表现 | 产品回应 |
|---|---|---|
| 信息分散、过期 | 微信群刷屏、传单、朋友圈，岗位真假难辨 | 按校区/距离/周末班次聚合，过期自动下架 |
| 时间不合 | 有课、已有安排、只空半天 | 班次级筛选 + 时间冲突校验 |
| 距离不透明 | 看着近，实际通勤 40 分钟 | 显示距离、步行/骑行预估，按 3km 筛选 |
| 怕被骗、怕白干 | 要先交押金、口头承诺工资、干完拖欠 | 商家认证标识、工资托管状态、履约留痕 |
| 首次兼职没经验 | 不知道要做什么、穿什么、几点到 | 工作卡、轻量 SOP、到岗提醒 |
| 一个人不敢去 | 陌生商家、陌生环境 | 同校报名人数、商家评价（组队为 P1） |

### 2.2 商家侧

| 痛点 | 具体表现 | 产品回应 |
|---|---|---|
| 临时缺人 | 周末高峰、员工请假，提前一天才缺 | 发布班次 + 候补池 + 一键补位 |
| 招人慢 | 群里发消息，响应零散 | 匹配候选人列表，按匹配分排序 |
| 爽约成本高 | 说好来，临时不来，生意受影响 | 信用分、爽约记录、候补自动递补 |
| 筛选成本高 | 不知道谁靠谱、谁能干 | 信用、完成次数、评价、技能标签 |
| 培训重复 | 每个人都要讲一遍 | 岗位 SOP 模板（P1 完整版，MVP 先展示要点） |
| 结算留痕难 | 工时、工资口头约定 | 签到签退、工时确认、模拟账本 |

### 2.3 平台侧

| 痛点 | 产品回应 |
|---|---|
| 双边冷启动 | 单校区试点，先积累 30 家高频商家和 300 名学生 |
| 虚假岗位/违规内容 | 商家认证、岗位巡检、关键词拦截、举报入口 |
| 纠纷无证据 | 报名确认、签到记录、工时确认、评价全部留痕 |
| 匹配效率与公平 | 可解释规则匹配，不用性别/学校做推荐，给新学生曝光 |

## 3. 产品定位与边界

### 3.1 一句话定位

**周末职得**：让大学生在周末有空时，10 分钟内找到距离近、时间合适、工资有保障的短工；让周边商家在高峰前快速补齐能到岗的学生人手。

### 3.2 价值主张

**对学生：**

- 只看看得懂的班次：几点、在哪、做什么、多少钱。
- 只报敢报的岗位：商家认证、工资托管、履约留痕。
- 只做合得来的时间：自动避开已确认班次，距离可筛。

**对商家：**

- 1 次发布，覆盖周边校园。
- 按匹配分看人，不用在群里翻消息。
- 有人不来，候补自动补位。
- 按成功履约付费（试点期免佣），不为无效曝光买单。

### 3.3 边界（不做什么）

- 不做全职/实习/校招，不做跨城。
- 不做社交动态、匿名树洞、兼职经验社区。
- 不做真实资金托管、真实支付、真实身份认证（演示态）。
- 不做黑盒 AI 自动录用；AI 只做文案辅助（P1）。
- 不鼓励超时工作：单日不超过 8 小时，周末不超过 16 小时。

### 3.4 试点设定（文档假设）

- 地点：虚构的「星湖大学城」，3km 生活圈，2 个校区。
- 供给：咖啡、餐饮、零售、宠物、活动执行、花店等 6 类商家。
- 需求：周末单次 4–8 小时为主，日薪 80–200 元。
- 规模假设：300 名学生、30 家商家、每周 60 个班次。

## 4. 用户与场景

### 4.1 角色

| 角色 | 目标 | 关键权限 |
|---|---|---|
| 学生 | 找到并完成靠谱的周末短工 | 浏览、报名、撤回、签到、评价、查看信用 |
| 商家 | 快速补齐周末人手并完成结算 | 发布/管理岗位、看候选人、录用/候补、确认工时、评价 |
| 运营 | 控制平台信任与履约风险 | 认证审核、岗位巡检、纠纷处理、看概览 |

### 4.2 Personas

**林小满 · 大二 · 新闻传播**

- 周末想赚 300 元生活费，但周六下午有社团活动。
- 只接受 2km 内，最好能坐地铁/骑共享单车。
- 第一次兼职，怕被骗押金，怕商家临时不要人。
- 决策因素：工资透明 > 距离 > 时间合适 > 商家评价 > 同学去过。

**陈姐 · 38 岁 · 社区咖啡店主**

- 周末客流是工作日两倍，固定员工忙不过来。
- 习惯在微信群发招人消息，常被放鸽子。
- 没有时间看长简历，只想知道「能不能来、靠不靠谱、会不会做」。
- 决策因素：到岗确定性 > 响应速度 > 上手能力 > 成本。

**周航 · 26 岁 · 平台运营**

- 每天处理商家认证、岗位投诉、履约纠纷。
- 需要快速判断证据、控制风险，避免平台变成虚假招聘温床。
- 决策因素：流程可追溯 > 处理时效 > 双边体验。

### 4.4 关键旅程

**学生首单：**

```text
打开链接 → 学生视角 → 看到「周六 10:00–18:00 · 1.2km · ¥160/天」
→ 详情页确认时间/工资/商家 → 报名（无冲突）
→ 商家录用 → 工作卡出现 → 签到 → 签退
→ 商家确认 → 工资入账（模拟）→ 评价 → 信用 +1
```

**商家补人：**

```text
工作台看到「周六缺 1 人」→ 发布班次 → 看到 3 位候选人
→ 录用匹配分最高者 → 候选人接受（演示自动）
→ 有人取消 → 候补自动递补 → 到岗名单更新
```

### 6.6 关键验收标准（节选）

**AC-STU-04 报名冲突**

```gherkin
Given 学生已有一个周六 10:00–16:00 的已确认班次
When 学生报名周六 14:00–18:00 的班次
Then 系统阻止报名
And 提示「与已确认班次时间冲突」
And 不产生新的报名记录
```

**AC-MER-04 录用**

```gherkin
Given 班次还剩 1 个名额
And 商家查看候选人列表
When 商家录用 1 名学生
Then 生成履约单，班次状态变为已满
And 该学生收到「已录用」通知
And 其他候选人仍可进入候补
```

**AC-ORD-04 签到**

```gherkin
Given 学生已录用，班次在签到窗口内
When 学生输入正确签到码并确认模拟定位
Then 履约单状态变为进行中
And 记录签到时间
And 商家端到岗名单同步更新
```

**AC-ORD-06 结算**

```gherkin
Given 商家已确认工时
When 系统执行模拟结算
Then 履约单变为已完成
And 学生钱包增加对应工资
And 商家账本出现一笔支出
And 页面显示「模拟结算，非真实资金」
```

## 7. 业务规则

| ID | 规则 |
|---|---|
| BR-01 | 报名资格：学生档案完整度 ≥ 80%，无平台限制；演示账号默认满足 |
| BR-02 | 时间上限：单班次 ≤ 8 小时，单日 ≤ 8 小时，周末 ≤ 16 小时；超过 4 小时须展示休息提示 |
| BR-03 | 报名上限：同时最多 3 个活跃报名；同一时段只能有 1 个已确认班次 |
| BR-04 | 薪酬透明：必须展示计薪方式（日薪/时薪）、金额、结算时间；学生端不收取任何费用 |
| BR-05 | 托管展示：商家发布即显示「工资已托管（模拟）」；未托管不可发布（演示统一为已托管） |
| BR-06 | 录用规则：名额未满才可录用；先到先得与匹配分并存，商家可自主选择；满员后只能候补 |
| BR-07 | 取消规则（演示版）：学生开始前 >24h 取消无扣分；12–24h 扣 3 分；<12h 扣 8 分；爽约扣 15 分。商家开始前 <24h 取消扣 5 分，并优先推荐替代班次 |
| BR-08 | 候补规则：候补按「报名时间 + 匹配分」排序；有空位自动递补；递补后 2 小时内未确认视为放弃（演示自动确认） |
| BR-09 | 签到规则：开始前 30 分钟至开始后 30 分钟；模拟围栏 300m；迟到 >15 分钟标记；超过 30 分钟可标记爽约。**演示模式放宽时间窗口，并在界面标注** |
| BR-10 | 结算规则：商家确认工时后进入待释放；24 小时无纠纷自动释放（演示加速为立即）；有纠纷则冻结 |
| BR-11 | 评价规则：仅已完成订单；双方各一次；1–5 星 + 标签；禁止辱骂/泄露隐私；评价不可修改 |
| BR-12 | 信用规则：初始 100，上限 120；完成 +1，五星 +1；迟到 -3；12–24h 取消 -3，<12h 取消 -8；爽约 -15；商家责任取消 -5；低于 60 限制报名高信任岗位；低于 40 暂停 7 天 |
| BR-13 | 内容规则：禁止押金/培训费/刷单/夜场/高风险作业；禁止性别、学校等歧视性要求（真实职业资格除外） |
| BR-14 | 隐私规则：录用前地址模糊、电话隐藏；录用后展示必要联系信息；不在演示中收集真实身份证/银行卡 |
| BR-15 | 公平规则：推荐不使用性别、民族、学校层次等受保护属性；新学生获得曝光加权；同一商家不过度占据推荐位 |
| BR-16 | 平台角色：信息撮合与履约工具，不是劳务派遣；真实上线前需法律与支付合规评审 |

## 9. 指标

### 9.1 北极星指标

**每周有效履约班次（完成签退并确认工时的班次）**。它同时代表学生赚到钱、商家补到人。

### 9.2 试点验证指标（真实上线后）

| 指标 | 目标 |
|---|---|
| 岗位 24h 填充率 | ≥ 80% |
| 报名→录用转化率 | ≥ 30% |
| 确认→到岗率 | ≥ 90% |
| 平均填补时长 | ≤ 4 小时 |
| 学生次月复购率 | ≥ 25% |
| 商家次月复聘率 | ≥ 40% |
| 纠纷率 | ≤ 3% |

### 9.3 本次演示验收指标

- 核心闭环 7 个状态节点全部可在线上走通；
- 三角色切换 ≤ 2 次点击；
- 关键页面无空白/报错；
- 390px 下核心按钮不被遮挡；
- 从打开链接到完成一次报名 ≤ 90 秒。

## 10. 风险与合规

| 风险 | 影响 | 应对 |
|---|---|---|
| 静态演示被误认为真实平台 | 信任/合规风险 | 全站演示标识；不出现真实支付入口；不收集敏感信息 |
| localStorage 数据丢失 | 演示中断 | 重置按钮；异常降级；种子数据内置 |
| GitHub Pages 访问不稳定 | 部署后链接打不开 | 使用者部署后多网络验证；保留手动上传 `dist/` 的备选方式 |
| 双边冷启动 | 真实产品无供给 | 单校区、高频商家、人工撮合前 50 单 |
| 爽约/纠纷 | 体验与成本 | 信用、候补、签到、证据链、运营介入 |
| 劳动用工合规 | 法律风险 | 18+、工时上限、禁高危、平台居间定位、法律评审 |
| 隐私与个人信息 | 合规风险 | 最小化收集、模糊地址、录用后可见、演示不收集 |
| 虚假岗位 | 信任崩塌 | 商家认证、岗位巡检、关键词、举报 |
| 范围反弹 | 无法按时上线 | P0 冻结；P1 写入后续；先部署再优化 |

## 11. 已确认决策

1. 接受「纯前端 + 演示数据」，不做真实后端。
2. 由使用者自行部署到自己的 GitHub 仓库，不绑定具体账号。
3. 品牌名使用「周末职得」。
4. 取消/信用规则按本文执行（演示版）。
5. 只保留学生/商家/运营三个入口，不做注册登录。

> 以上不阻塞演示实现，但会影响最终验收口径。
