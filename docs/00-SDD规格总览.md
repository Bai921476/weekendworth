## 1. 为什么用 SDD

SDD（Specification-Driven Development，规格驱动开发）把规格当作开发与验收的唯一事实来源，而不是先写代码、再补文档。

本项目用 SDD 解决三个具体问题：

1. **双边平台容易功能发散**：学生、商家、运营三端互相牵制，必须先定边界。
2. **AI Coding 容易跑偏**：生成速度快，没有验收标准就会反复返工。
3. **最终只能交一个链接**：线上可操作是硬指标，规格必须围绕「可演示闭环」而不是「功能清单」。

本项目的四条原则：

- **规格先于代码**：P0 功能先有需求 ID 和验收标准，再实现。
- **演示优先**：每个功能都要能在浏览器里被看到、被操作。
- **真实边界**：模拟支付、模拟定位、演示数据必须明确标注，不冒充真实能力。
- **不过度设计**：不做后端、不做真实登录、不做真实交易，把时间留给撮合与履约。

## 2. 规格层级

```text
L0 问题与定位
   └─ 用户痛点、产品边界、成功指标
L1 需求规格（What）
   └─ 角色、场景、功能需求、业务规则、非功能需求
L2 技术规格（How）
   └─ 静态架构、数据模型、状态机、匹配算法、部署验证
L3 产品与验收（Proof）
   └─ 页面结构、流程、设计系统、演示脚本、验收清单
```

| 文档 | 回答的问题 | 不负责 |
|---|---|---|
| 01 需求分析 | 为谁解决什么问题？做到什么程度？ | 技术实现、页面细节 |
| 02 技术规范 | 单页应用如何组织？数据与状态如何流转？如何上线？ | 视觉风格、运营策略 |
| 03 产品设计与验收 | 用户看到什么、怎么操作、怎么证明完成？ | 重新定义需求 |

## 3. 编号与追溯

| 前缀 | 含义 | 示例 |
|---|---|---|
| `FR-STU-xx` | 学生端功能 | FR-STU-03 筛选班次 |
| `FR-MER-xx` | 商家端功能 | FR-MER-02 发布岗位 |
| `FR-ORD-xx` | 履约/订单 | FR-ORD-03 签到 |
| `FR-ADM-xx` | 运营视角 | FR-ADM-01 认证审核 |
| `FR-SYS-xx` | 通用能力 | FR-SYS-01 角色切换 |
| `BR-xx` | 业务规则 | BR-06 取消规则 |
| `NFR-xx` | 非功能需求 | NFR-02 性能 |
| `AC-xx` | 验收标准 | AC-ORD-01 |
| `T-xx` | 测试用例 | T-E2E-01 |

追溯链：

```text
用户故事 US → 功能需求 FR → 页面（03）→ 状态/数据（02）→ 测试 T（03）→ 线上验收
```

**规则：** 没有 FR 编号的功能不做；没有验收标准的 FR 不算完成。

## 4. 变更控制

### 4.1 本次范围变更（v0.1 → v0.2）

| 变更 | 原因 | 影响 |
|---|---|---|
| 全栈改为纯前端静态 SPA | 原型不需要后端，降低构建与部署门槛 | 删除 Express/SQLite/API/服务端鉴权 |
| 真实能力改为演示态 | 无支付/地图/实名资质，不应假装接入 | 页面统一标注「演示」 |
| 运营后台缩减为轻量视角 | 保留信任闭环，砍掉非核心管理功能 | 只保留认证、巡检、纠纷入口 |
| 组队、AI、复聘、多校区移出 MVP | 聚焦最小可演示闭环 | 写入 P1/后续 |
| 5 份文档合并为 3 份 + 总览 | 减少文档开销 | 产品与验收合并 |

### 4.2 什么时候必须改规格

- 新增/删除 P0 功能；
- 改变角色权限或关键规则（取消、结算、信用）；
- 改变核心数据结构或状态机；
- 改变部署方式或验收口径。

变更流程：更新本文档决策记录 → 更新 01/02/03 → 更新验收清单 → 再改代码。

### 4.3 版本规则

- `v0.x`：评审草案；
- `v1.0`：评审通过，进入实现；
- `v1.x`：实现期澄清；
- `v2.0`：MVP 范围或核心规则变化。

## 5. 完成定义（Definition of Done）

一个 P0 功能算完成，必须同时满足：

- [ ] 有 FR 编号与验收标准；
- [ ] 页面和交互在 03 中有规格；
- [ ] 数据/状态变化在 02 中有定义；
- [ ] 正常路径 + 至少 2 个异常路径可操作；
- [ ] 390px 与 1440px 均可用；
- [ ] 无阻塞性控制台错误；
- [ ] 已更新 03 的验收记录。

**项目级完成定义：**

- [ ] 构建通过（TypeScript + Vite）；
- [ ] 静态产物可直接部署到 GitHub Pages 子路径；
- [ ] 核心闭环可操作；
- [ ] 刷新不丢演示数据，且可一键重置；
- [ ] 交付源码、构建产物与可选的 GitHub Actions 示例，由使用者自行部署。

## 6. 关键设计决策

| ID | 决策 | 理由 | 影响 |
|---|---|---|---|
| ADR-001 | 以「班次 Shift」而非「岗位 Job」为撮合单位 | 周末用工差异在具体时段、人数、薪资 | 岗位含多个班次；报名针对班次 |
| ADR-002 | 纯前端静态 SPA，无后端 | 原型零运维、构建简单 | 数据存 `localStorage`；无跨设备同步 |
| ADR-003 | 演示数据 + 角色切换，不做真实登录 | 评审重点看产品闭环，不看重账号体系 | 一键切换学生/商家/运营 |
| ADR-004 | 工资托管只做「状态与账本展示」 | 无支付牌照与真实资金，不能假装交易 | 标注「模拟托管」，不出现真实支付入口 |
| ADR-005 | 匹配采用「硬约束 + 可解释评分」 | 公平、可解释、方便演示 | 规则引擎 + 匹配理由；不做黑盒 AI |
| ADR-006 | Hash 路由 + 相对资源路径 | GitHub Pages 子路径部署无需服务端重写 | 链接形如 `.../<repo>/#/student` |
| ADR-007 | 先模块化单体前端，不引入状态管理库 | 规模小，React Context + reducer 足够 | 减少依赖与构建风险 |
| ADR-008 | 交付可部署源码 + 可选 Actions 示例 | 使用者自行部署，避免代替账号操作 | 当前线上使用 gh-pages 分支发布 |

## 7. 术语表

| 术语 | 定义 |
|---|---|
| 班次 Shift | 一段具体工作时间、人数和薪资，是报名与履约的最小单位 |
| 岗位 Job | 商家发布的一条招聘信息，包含一个或多个班次 |
| 候选人 Application | 学生对某个班次的报名记录 |
| 履约单 Order | 商家录用后形成的执行记录，承载签到、结算、评价 |
| 候补 Waitlist | 班次满员后的排队，出现空位时递补 |
| 托管 Escrow | 演示态的工资保障状态，不代表真实资金 |
| 信用分 Credit | 平台内履约行为的量化记录，不是社会信用 |
| 补位 | 班次缺人时向匹配学生批量推送并快速确认 |

## 8. 评审检查清单

- [ ] 是否聚焦「周末 + 周边 + 短工」，而不是泛招聘？
- [ ] 是否同时解决学生「怕被骗/时间不合」和商家「怕爽约/招人慢」？
- [ ] 信任与履约是否闭环：认证、托管、签到、评价、纠纷？
- [ ] 缩减后的 P0 是否还能讲清楚产品价值？
- [ ] 是否明确标注演示数据与模拟能力？
- [ ] 构建与静态部署路径是否已验证？
- [ ] 是否交付了可直接部署的源码，而不是只存在于本地临时环境？
